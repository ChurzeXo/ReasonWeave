# 20 — Vibe Coding 虚假安全感穿透防御与依赖可达性治理

> 本章回答一个高危工程现象：**AI Agent 辅助编程（Vibe Coding）能让功能飞速跑通，但也会引入极其逼真的“虚假安全感（False Sense of Security）”**。
> **理论与实践背书**：斯坦福大学 CS146S《现代软件开发者》第 6 周安全实操、ADR-0011 与 ADR-0012 架构决议；机件位于 `units/review-gate/` 与 `units/orphan/`。

---

## 1. 现象与定位：什么是“虚假安全感”？

在 Coding Agent（Claude Code, Cursor, Windsurf 等）普及后，软件开发最危险的状态不再是“代码跑不起来”，而是**“表面全绿灯、测试全通过，但内部潜伏高危隐患”**。

在传统开发中，工程师对安全报警有敬畏心；而在 Agent 自主迭代中，Agent 面临强烈的“闭环交付偏见（Completion Bias）”。当门禁报错时，Agent 最擅长的不是深度重构，而是**“如何用最小的 Token 成本让报错消失”**——这催生了自欺欺人的虚假安全感。

---

## 2. 四大核心反模式（CS146S 实操启示）

| # | 反模式 | 表现形式 | 致命后果 |
|---|---|---|---|
| **A1** | **免检声明当证明** | Agent 在遇到静态扫描报错时，直接在行尾追加 `# noqa`、`# nosem` 或 `// nolint` | 用户表达式执行（`eval`）、系统命令注入（`subprocess` shell=True）、SSRF 等漏洞被合法掩盖，SAST 沦为装饰品。 |
| **A2** | **孤儿依赖引发警报风暴** | `requirements.txt` / `package.json` 长期只增不减，声明 9 个包其实只有 5 个真正被导入 | 扫描器报出 50+ 条高危 CVE 公告，引发严重的告警疲劳（Alert Fatigue），导致真正在用的受灾包被淹没。 |
| **A3** | **碰巧够不着当作安全** | 依赖存在已知 CVE，但当前业务逻辑碰巧只调用了其无害方法（如 `load_dotenv()` 没触及危险反序列化），于是口头忽略 | **今天碰巧够不着 ≠ 安全**。未来重构一旦调用该模块其他函数，漏洞瞬间激活；口头放行破坏了长期可追溯性。 |
| **A4** | **工具缺失时虚报实测** | 运行环境中缺少指定 SAST 工具（如 Semgrep / OpenGrep），自动化流程静默跳过并在回执中声称“已实测无漏洞” | 彻底破坏了 AEF 最高宪法的“诚实边界（Honesty Invariant）”，产生伪造通过。 |

## 3. 防护战法与硬核纪律

### 战法 1：Anti-Suppression 穿透审计（“免检不是证明”）
* **铁律**：源码行尾的 `# noqa` / `# nosem` 一律视作“未经验证的主观断言”。
* **机器化对策**：
  * 在安全扫描与发布门禁中，强制执行 **穿透模式（`--no-suppress`）**：
    ```bash
    # review-gate 穿透扫描命令
    bash review-gate/scan.sh --no-suppress
    ```
  * 剥离所有行内免检注释后比对 Findings。合法误报**必须显式写入 `baseline.json` 并附带人类 Reviewer 签名**，禁止源码行内随意裸写绕过。

---

### 战法 2：孤儿依赖清洗（先降噪，再审计）
* **铁律**：依赖清单必须与代码树 AST 实际 `import` 保持双向零差集。
* **机器化对策**：
  * 在跑重量级 CVE 扫描前，必须先调用 `units/orphan` 的依赖对账探针：
    比对清单声明 vs 代码中实际的 `import / require`。
  * 将 0 引用的孤儿包踢出清单后，再执行漏洞扫描，物理切除 90%+ 的虚假告警噪音，让注意力聚焦于真正生效的调用链。

---

### 战法 3：漏洞可达性研判（Reachable CVE Triage）与硬闭环
* **铁律**：严禁对调用图未达（Unreachable）的已知 CVE 进行静默放行。
* **机器化对策**：
  * 当分析确认当前业务仅调用无害函数、决定暂缓升级时，**必须在 `docs/backlogs/` 或 `docs/adr/` 建立显式追踪单**：
    1. 记录受灾包名及当前锁定版本；
    2. 记录 CVE 漏洞原理与危险入口函数；
    3. 记录当前代码调用链未达的物理证据（AST Call Graph）；
    4. 设定重审触发条件（如：业务新增该包其他导入、或上游发布 Patch）。
  * 严禁无凭据的口头豁免。

---

### 战法 4：测试先行负向护栏（先红后绿）
* **铁律**：修复安全漏洞必须遵循测试驱动安全（Security TDD），不接受“口头已修复”。
* **机器化对策**：
  * 修复漏洞或处理边界缺陷前，必须先编写能够触发漏洞的 **Exploit 负向测试（Negative Test）**；
  * 验证该测试在修复前的代码上稳定报错（`exit != 0`）；
  * 代码修复完成后，重新运行该测试直至转绿（`exit == 0`）；
  * 交付回执必须附带由 `baton-audit-runner`（Clean Runner）独立重跑的 Exit 0 物理证据。

---

### 战法 5：诚实降级阶梯（Honesty Invariant）
* **铁律**：环境缺失重型工具时允许降级，但未实测严禁谎称实测。
* **机器化对策**：
  * 当缺少 OpenGrep 二进制时，`review-gate` 自动降级为极速单二进制探针：
    `ruff check --select S`（Flake8-Bandit 规则集）+ 本地敏感正则；
  * 门禁与交接回执中必须显式输出 `engine: fallback-ruff-bandit`，保持机器证据完全诚实透明。

---

## 4. 落地接入命令汇总

| 目标场景 | 执行命令 | 预期效果 |
|---|---|---|
| **常规提交前静态扫描** | `bash review-gate/scan.sh` | 拦截基线外的新发现 |
| **穿透式无免检安全审计** | `bash review-gate/scan.sh --no-suppress` | 忽略 `# nosem`，揪出所有隐藏漏洞 |
| **轻量级环境 Fallback 扫描** | `ruff check --select S .` | 毫秒级捕获 Python 常见高危安全漏洞 |
| **独立双盲验证验收命令** | `baton-audit-runner run <id> --auto-receipt` | 隔离上下文独立重跑，杜绝自测自欺 |
