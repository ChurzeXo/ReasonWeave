# 系统化排错技能 (Systematic Debugging)

## 核心原则 (Core Principle)
**未查明根本原因（Root Cause）前，绝对禁止尝试修改代码。治标不治本是工程失败的根源。**

## 不可违背铁律 (The Iron Law)

```text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
（未经根因调查证实，严禁编写任何修复代码）
```

如果你还没有完成 Phase 1（根因调查），你没有任何资格提出修复方案或动手改代码。

---

## 适用场景 (When to Use)

用于所有技术异常：
- 单测与集成测试失败
- 运行时报错或未捕获异常
- 构建与编译报错
- 性能瓶颈与超时
- 环境变量、配置与路径异常

**在以下情境下尤其必须强制执行：**
- 时间紧迫（越急躁越容易瞎猜）
- 觉得“这只是个简单的 Quick Fix”
- 之前尝试的修复没有起效
- 你并没有 100% 搞懂底层数据流

---

## 防合理化阻断表 (Anti-Rationalization)

大模型在排错时极易寻找借口跳过根因分析。以下念头出现时，**必须立刻停止**：

| 借口 (Thought) | 现实 (Reality) |
| :--- | :--- |
| “我大概知道哪里的问题了，先改一行试试” | 凭猜想改代码只会引入次生缺陷。停下来，拿出证明。 |
| “这个 Bug 很小，不用搞 4 个阶段” | 小 Bug 同样有根因。跳过根因分析是返工的第一诱因。 |
| “改这里比较快，不行我再 revert” | 盲目试错会污染 Git 记录与上下文，破坏思考连贯性。 |
| “测试挂了是因为期望值写错了，我改下测试” | 严禁直接放宽断言！必须先核实是被测代码逻辑错还是契约改动。 |
| “这肯定是第三方依赖或环境的锅” | 99% 的问题出在自身调用与配置，先拿出外部组件损坏的铁证。 |
| “我已经试了两次了，第三次肯定行” | 已经连续试错说明假设全错。必须回到第一阶段重新看日志。 |

## 系统化排查四阶段 (The Four Phases)

必须依次完成以下 4 个阶段，严禁跨阶段跳跃：

### Phase 1: 根因调查 (Root Cause Investigation)

在动手写任何修复代码之前，必须完成：
1. **完整详读报错信息**：
   - 不得略过 Warning、Stack trace 或状态码；
   - 标注具体报错文件名、精确行号与错误代号。
2. **稳定复现（Consistent Reproduction）**：
   - 确定最小复现步骤；如果无法稳定复现，继续增加日志插桩，严禁瞎猜。
3. **比对最近变更（Diff & Invariants）**：
   - `git diff`、最近 commits、依赖版本锁定变动、环境差集。
4. **多组件边界诊断插桩（Instrumentation）**：
   - 当系统涉及多层（如 CI $\to$ 脚本 $\to$ 进程，或 Controller $\to$ Service $\to$ DB）：
   - 在组件边界处输出真实出入参（真实环境变量、入参类型、返回值），精准定位故障停在哪一层。
5. **数据流逆向回溯（Data Flow Tracing）**：
   - 错误值从哪一层传入？谁调用了它？一路向上追溯到污染源头，在源头解决，而不是在报错点打补丁。

### Phase 2: 模式比对 (Pattern Analysis)

1. **寻找同仓成功样板**：同一代码库中是否有相似功能正常工作？
2. **逐行对照权威实现**：比对工作正常与损坏的代码，列出所有差异，不要主观假设“这不可能有影响”。
3. **依赖与环境假设核查**：当前运行环境是否缺失隐式假设（如 Node 版本、目录权限、环境变量）。

### Phase 3: 假设建立与极简验证 (Hypothesis & Testing)

1. **明确单一假设**：明确写出：“我认为根本原因是 X，因为证据 Y”。
2. **单变量极简验证**：只改变一个变量验证假设，严禁多点同时修改。
3. **验证假设真伪**：
   - 若证实假设 $\to$ 进入 Phase 4；
   - 若假设推翻 $\to$ 重新建立假设，严禁在错误假设上打补丁叠加。

### Phase 4: 根治实现与回归闭环 (Implementation & Verification)

1. **先写失败的测试（Red Test First）**：
   - 构造能精准复现该根因的极简失败测试用例（遵循 `test-driven-development` 技能）；
   - 亲眼确认测试在未修复前必然报错。
2. **单一根治修复（Single Fix）**：
   - 针对根因编写最小修复代码；严禁夹带重构或“顺手做”的改动。
3. **双向回归验证（Verification）**：
   - 该失败用例转绿；全量回归测试保持全绿；
   - 遵循 `verification-before-completion` 技能，当场运行真实命令验证 Exit 0。
4. **三振出局原则（Architecture Escalation）**：
   - **如果连续尝试 3 次修复均告失败，立刻停止！**
   - 禁止盲目尝试第 4 次修复；这表明该问题不是局部实现 Bug，而是架构设计或底层假设存在缺陷；
   - 立即向人类架构师汇报，阐明已知证据，重新审视技术路线。
