# 测试驱动开发技能 (Test-Driven Development)

## 核心原则 (Core Principle)
**先写测试，亲眼目睹其失败，再写满足测试的最小实现代码。**  
如果你没有亲眼看到测试失败，你就根本不知道这个测试是不是在测目标逻辑。

## 不可违背铁律 (The Iron Law)

```text
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
（未先编写并运行失败的测试，严禁编写任何生产代码）
```

先写了生产代码？**删掉，从测试重新开始。**  
不得保留作为“参考”，不得“边看边写”，删掉就是彻底重构。

---

## 适用场景 (When to Use)

- **新功能与新原语开发**
- **所有 Bug 修复**（先写能重现 Bug 的单测）
- **内部重构与性能优化**
- **行为或契约微调**

**唯一豁免情形（须人类明确批准）：**
- 纯丢弃型探索 Prototype（实验分支）
- 工具自动生成的静态配置或元数据
- 纯文档说明撰写

---

## 防合理化阻断表 (Anti-Rationalization)

| 借口 (Thought) | 现实 (Reality) |
| :--- | :--- |
| “功能太简单了，写完实现再补测试一样” | 先写实现后补测试，往往只会写“通过的伪测试”，失去保护力。 |
| “我先把结构搭好，等下写测试” | 骨架也是代码。先写测试能倒逼出最简洁舒适的 API 接口。 |
| “测试框架搭起来太麻烦了” | 没有单测的项目维护成本是几何级暴增。哪怕写单文件临时探针也必须测。 |
| “我先写一点实现代码当草稿参考” | 人的心理惯性会导致草稿直接变成生产代码。从测试驱动。 |
| “这次改动只是个小重构，不用新写测试” | 重构的定义是在有测试网保护下调整内部结构。没有测试不叫重构，叫冒险。 |

---

## 红-绿-重构循环 (Red-Green-Refactor)

```text
  ┌───────────────────────────────────────────────┐
  │ 1. RED (红灯)                                 │
  │    编写极简单测，断言预期的正确行为             │
  │    运行测试，确保 100% 失败并抛出预期错误原因  │
  └───────────────────────┬───────────────────────┘
                          │
                          ▼
  ┌───────────────────────────────────────────────┐
  │ 2. GREEN (绿灯)                               │
  │    编写能够让该测试通过的「最小生产代码」       │
  │    严禁过度设计，严禁提前写未经测试的逻辑      │
  │    运行测试，见证全绿                           │
  └───────────────────────┬───────────────────────┘
                          │
                          ▼
  ┌───────────────────────────────────────────────┐
  │ 3. REFACTOR (重构)                            │
  │    消除重复代码 (DRY)，优化命名与架构结构       │
  │    每次小改后重新跑测，确保「持续保持绿灯」     │
  └───────────────────────────────────────────────┘
```

### 1. RED: 编写极简失败测试
- **测试真实行为，而非 Mock 实现细节**：
  - 测试应该关心“输入 X，产出 Y”，而不是测试“函数内部是否调用了私有方法 Z”。
- **确认失败信息具有可解释性**：
  - 测试报错必须准确指出业务逻辑不符（如 `Expected 200, got 404` 或 `Expected token to match signature`），而不是因为拼写错变量名抛出的语法错误。

### 2. GREEN: 编写最小可过代码
- 秉持 **YAGNI (You Aren't Gonna Need It)** 原则；
- 只写能满足当前测试所必需的代码，不盲目预留扩展接口；
- 运行测试套件，确认单测通过且历史测试无 Regression。

### 3. REFACTOR: 清理重构
- 提取常量、消除重复、优化模块边界；
- 每做一步重构，立即跑测试；一旦变红立刻 revert 并重新审视。
