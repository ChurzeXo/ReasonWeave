# 先验后报技能 (Verification Before Completion)

## 核心原则 (Core Principle)
**真实证据永远先于结论主张（Evidence Before Assertions, Always）。**

## 不可违背铁律 (The Iron Law)

```text
NO COMPLETION CLAIMS WITHOUT FRESH VERIFICATION EVIDENCE
（未经当前消息中执行真实命令获取新鲜证据，严禁声称任何任务完成）
```

如果你在当前这一轮交互中没有运行过能够证明你主张的真实物理命令，你绝对不能说“完成了”、“测试通过了”或“问题解决了”。

---

## 门禁核验五步法 (The 5-Step Gate Function)

在向人类或调用方表达任何完成、满意或就绪状态之前，必须严格执行：

1. **识别判据 (IDENTIFY)**：哪条具体的物理命令可以无可辩驳地证明这个任务已完成？（如 `npm test`、`npm run build`、`git diff --check`）
2. **当场执行 (RUN)**：在当前轮次完整执行该命令，不得依赖历史记录或“刚才跑过”。
3. **详读输出 (READ)**：阅读完整的输出流，核实子进程 Exit Code 是否为 0，核实失败数（Failure/Error Count）是否为 0。
4. **证据对照 (VERIFY)**：输出内容是否 100% 证实了预期？
   - 若否：如实汇报未通过状态与具体失败报错；
   - 若是：带着该命令的确切输出与证据路径，阐明结论。
5. **方可陈述 (ONLY THEN)**：方可正式声称任务完成或回执就绪。

**跳过以上任何一步，在工程伦理上等同于“制造假自律与虚假安全感”。**

---

## 防合理化阻断表 (Anti-Rationalization)

大模型在疲劳或长上下文时，常常习惯性用礼貌或积极情绪敷衍了事。以下念头出现时，**必须立刻停止**：

| 借口 (Thought) | 现实 (Reality) |
| :--- | :--- |
| “代码逻辑改得这么严密，应该没问题了” | “应该”不等于物理事实。立即运行测试命令。 |
| “我改动很小，编译通过了就不跑测试了” | 编译通过只能证明语法合法，完全不证明业务逻辑不回退。 |
| “刚才子 Agent 回报说它测试过了” | 永远独立重新跑一遍。子 Agent 也可能产生幻觉或虚假上报。 |
| “上下文快满了，跑命令太耗 token” | 交付一个未经验证的坏改动，后续排查要消耗 10 倍的 token。 |
| “我用了与之前测试相同的逻辑，肯定行” | 相同逻辑在不同分支或依赖下完全可能行为迥异。必须当场出证。 |
| “时间太晚了，我就写句搞定交差” | 严厉杜绝浮夸或欺瞒。宁可陈述未验，不可宣称已过。 |

## 常见主张所需的确切物理证据

| 主张陈述 (Claim) | 必须具备的物理证据 (Requires) | 不充分的借口 (Not Sufficient) |
| :--- | :--- | :--- |
| **测试全部通过** | 测试命令 Exit Code 0，且终端输出 `0 failures` | “之前跑过通过了”、“代码看起来完全合规” |
| **Lint / SAST 无报警** | 扫描器退出码 0，且明确报告 `0 errors` | 部分文件手测、肉眼审查无异常 |
| **构建成功** | 编译构建脚本 Exit 0，产出物物理存在 | 静态类型检查绿灯、日志看起来没问题 |
| **Bug 已修复** | 原先复现该 Bug 的失败用例当场转绿 | 只是改掉了报错处的代码行 |
| **功能已履约完成** | 针对需求 Checklist 逐行核对并输出对账表 | “核心流程通了，其他应该可以” |

---

## 危险辞藻红线 (Red Flags)

在尚未取得真实命令结果前，回复中严禁出现以下倾向性词汇：
- “应该已经修复了” (Should be fixed)
- “看起来很完美” (Looks good / Perfect)
- “大概率通过了” (Probably passes)
- “毫无疑问没问题” (Undoubtedly works)

**只有客观事实：命令是什么，Exit Code 是几，失败数是几。**
